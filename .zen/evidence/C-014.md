## Embedding experiments (2026-10-18, SumatraPDF 3.6 at `C:\Program Files\SumatraPDF`)

Scripts in the session scratchpad (`pdfexp/embed.ps1`, `pdfexp/drive.ps1`), a WinForms panel as the host:

- `SumatraPDF.exe -plugin <hwnd> <pdf>` creates its frame as a child (`SUMATRA_PDF_FRAME`, style
  `WS_CHILD | WS_VISIBLE | WS_CLIPSIBLINGS | WS_CLIPCHILDREN`) of the given window, sized to the parent at that
  moment, with its own toolbar (page field, arrows, view modes, rotation, zoom, find) and the canvas below. The
  document rendered inside the host; `PrintWindow(host, PW_RENDERFULLCONTENT)` captures it with the child.
- The frame does not follow a resize of its parent: `MoveWindow(frame, 0, 0, w, h, TRUE)` resizes it and the
  canvas re-lays out (captured at 600×500 after a 900×700 start).
- `WM_COPYDATA` to the frame with `dwData = 0x44646557` ("DdeW") and the UTF-16 DDE command text drives that
  instance alone, no DDE server involved (several instances register the same `SUMATRA` service, so a real DDE
  conversation could land in the user's own SumatraPDF): `[GotoPage("<path>", 3)]` went to page 3,
  `[SetView("<path>", "continuous", 50)]` set the zoom to 50 % with Sumatra's own notification; both returned 1.
  After a command Sumatra takes the keyboard focus (`GetFocus` and `GetForegroundWindow` were the frame).
- Closing the host window ends the SumatraPDF process on its own (`HasExited` true two seconds later); the
  view still kills it explicitly when the tab closes, so no instance outlives its tab.
- Not tried: `-plugin` with a URL argument (the browser-plugin form), the named-destination command (P-009).

## Design (2026-10-18)

- `src/tools.rs`: `Tool` (SumatraPdf, SevenZip, LibreOffice, Vlc, MuTool, PdfToPpm, PdfInfo), `ToolSet`
  (`from_env`, or `stubbed` for tests: an override per tool, a path or nothing) with `find` (override, else
  `SFOGLIA_<TOOL>` from the environment, else the registered handler and the known install folders, else the
  search path), `refresh` (looks again), `Found { path, version }` (the version resource on Windows read through
  `GetFileVersionInfoW`, `mutool -v` / `pdftoppm -v` otherwise), `status_line` (`SumatraPDF 3.6` /
  `mutool 1.24.9` / `<Tool> at <path>` / the install hint). The hint names the tool, the package or the site, and the
  override variable.
- `src/pdf_host.rs` (Windows only): `SumatraHost::start(exe, pdf, parent_hwnd)` spawns the plugin process;
  `place(bounds)` finds the frame among the parent's children by process id (several PDF tabs share the parent)
  and `MoveWindow`s it when the bounds change; `show(bool)` hides it when the tab is inactive or the hex view is
  on; `command(text)` sends the DDE text by `WM_COPYDATA`; `Drop` kills the process. The parent is the GPUI
  window's HWND from `raw_window_handle::HasWindowHandle` (a headless test window has none: the host is then
  not started and the view says so in its state, not on screen).
- `src/pdf_pages.rs` (both platforms): `Renderer` over `mutool` (`mutool pages` for the count and media boxes,
  `mutool draw -F png -r <dpi> -o <png> <pdf> <n>` per page) or `pdftoppm` with `pdfinfo` from the same package
  (`pdfinfo -f 1 -l N` for the sizes, `pdftoppm -png -r <dpi> -f n -l n -singlefile`), page images decoded by
  the image crate into `RenderImage`s, rendered on demand around the visible range into a temp folder removed
  with the view.
- `src/viewers/pdf_view.rs`: on Windows the Sumatra host when SumatraPDF is found, else the page renderer when
  mutool or pdftoppm is found, else the hint; on Linux the renderer or the hint. The status row names the tool
  and version and, in the page view, the page count, the current page and the zoom; Ctrl+= / Ctrl+- / Ctrl+0
  step the zoom and return to fit-width; `Look again` on the hint re-runs the detection. Without a tool the view
  shows the bytes (the hex view, C-007) under the hint.
- The workspace routes `Family::PdfXps` to the view and carries the `ToolSet` as it carries the rules store;
  `FilePanel::set_active` (the dock's hook) and the hex toggle hide and show the host.
- Fixture: `tests/fixtures/three.pdf`, three pages written by `cargo run -p xtask -- fixtures` (a hand-rolled
  PDF 1.4 with Helvetica text, correct xref offsets), and stub tools under `tests/stubs/` (`mutool.cmd` /
  `mutool.sh`: `-v` prints a version, `pages` prints two pages of different sizes, `draw` copies a fixture PNG;
  a stub that exits 1 for the failure path).

## Implementation notes (2026-10-18)

- Two defects found by the headless tests before any refuter pass. A page whose drawing failed was asked for
  again on every paint (the stand-in renderer run from a copied script could not find its fixture, and the test
  binary spawned a renderer process per frame until killed): a failed `(page, dpi)` is now remembered and not
  asked again until the zoom changes or `Look again` runs; the first complaint stays in the status row. And a
  tab the dock closed stayed in the workspace's list of open files until the next open, so its panel, its view,
  its SumatraPDF process and its folder of drawings lived on: the workspace forgets closed tabs on every render,
  and `the_drawings_folder_goes_with_the_tab` pins the view's drop through a weak handle.
- GPUI's `Window` has a `window_handle` of its own (the `AnyWindowHandle`), which shadows the
  `raw_window_handle` trait method: `raw_window_handle::HasWindowHandle::window_handle(window)` in full.
- The kit's `Root` wraps the window's view: `window.root::<Workspace>()` is `None` in tests, the entity from
  `open_window` is the one to keep.
- A stand-in script copied elsewhere loses its fixtures (`%~dp0` is the copy's folder): the test that makes a
  tool appear later writes a wrapper that calls the stand-in in place.
- The version banner parser takes digits and dots alone (`mutool version 9.9`): a `9.9-stub` would read as none.

## Windows captures (2026-10-18, before the first refuter pass)

- `scripts/windows-capture.ps1` learned two things for this clause: a hosted child window another process owns is
  not part of the GPUI surface `PrintWindow(PW_RENDERFULLCONTENT)` renders, so the script prints each
  `SUMATRA_PDF_FRAME` child on its own through `WM_PRINT` (flag 0; the DWM path gave a blank surface for it)
  and composes it at its place (`hosted=N` in its output); and `FindWindowExW` needs `[NullString]::Value` for
  the title, since PowerShell turns `$null` into an empty string, which matches no titled window.
- `runs/C-014-windows.png`: `three.pdf` opened from the command line; the tab, SumatraPDF's toolbar and page 1
  inside the panel (the frame at 80,122-1280,860 of the 72,61-1288,900 window: below the tab bar, above the
  status row), the status row `PDF · SumatraPDF 3.6 · the page, find, zoom, rotation and view controls are
  SumatraPDF's own`.
- `runs/C-014-windows-hex.png`: Ctrl+Shift+B pressed through the desktop-control tools: the bytes (`%PDF-1.4`)
  in the hex view, the frame hidden (`IsWindowVisible` false, the process alive); pressed again, the frame
  visible again.
- `runs/C-014-windows-page3.png`: the window resized from outside to 900×700 (`MoveWindow` on the main
  window): the frame followed to 80,122-964,721; then `[GotoPage("...three.pdf", 3)]` sent by `WM_COPYDATA`
  to the frame returned 1 and page 3 shows with `3 / 3` in SumatraPDF's own page field.
- The window closed through its close message (`CloseMainWindow`): no `sfoglia.exe` and no `SumatraPDF.exe`
  left. A forced kill of Sfoglia (the capture script's `Stop-Process -Force`, the first time) had left the
  SumatraPDF process behind: every hosted process now joins a kill-on-close job, so the system ends them when
  Sfoglia ends however it ends.
- The desktop-control tools cannot show SumatraPDF's window (the user declined that grant): the captures above
  are PrintWindow compositions, and the real screen was not looked at by the agent.
- The job proven: the app rebuilt, `three.pdf` hosted (`hosted=1` in the capture), `taskkill /F` on
  `sfoglia.exe`: no `SumatraPDF.exe` two seconds later.

## Refuter passes

- First pass (commit 59387e5): refuted. Eight mutations passed every test: the fit zoom without the gap and the
  pt→px factor, the page at the top fixed at 1, a failed drawing asked again on every paint, every page drawn
  at once, pdfinfo left out of `Look again`, the `+`/`=` bindings removed, the override variable ignored, the
  search path searched before the known places. Two defects by reading: one page's drawing failure replaced
  the summary for the life of the tab, with no `Look again` in page mode; and pdftoppm without pdfinfo was
  run as its own lister (`pdftoppm -f 1 -l 1000000 file`, which would render every page). Fixed: a drawing's
  complaint follows the count while that page stays undrawn and goes when it draws or the zoom changes; the
  listing's complaint offers `Look again`; without pdfinfo nothing is run and the hint is the complaint. Pinned:
  the fit zoom against the column's width and the page boxes against it, `+` and `=` pressed, the page at the
  top at the column's bottom by the test's own geometry, eight pages drawn around the viewport and after a
  scroll to the end (the stand-in logs each drawing), a page that fails to draw tried once per zoom, pdfinfo
  found by `Look again` and the poppler path drawing through its own stand-ins, the search order over a fixed
  environment (variable, known places, path, a variable to nothing, a missing place), the installed SumatraPDF
  by its full path (its registered handler names the same file, now looked at before the install folders).
  Found on the way: a long complaint pushed `Look again` out of the status row (the summary now truncates with
  an ellipsis, the tool and the button keep their width); batch stand-ins need `exit 1` inside a parenthesised
  block (`exit /b 1` there leaves 0 to the caller) and `shift /1` for a tenth argument.
- Second pass (commit fbc4456, after a crash of the agent's own process cut the first attempt short and
  corrupted the git index and two source files, both restored from HEAD): every first-pass pin caught its
  mutation; refuted on three new holes and one wording gap. (1) A tab that went behind another before
  SumatraPDF created its frame kept the frame visible at the full client size, over the tab bar: the frame was
  found only on paint, and a tab behind never paints; and the kit's dock calls no `set_active` at all, so the
  first tab never heard it went behind. Fixed: the view polls for the frame every tenth of a second after the
  start and hides it the moment it is found when its tab is hidden; the workspace tells every panel on each
  render whether the dock shows it (the active tab of each group). Pinned headlessly (two PDFs open, the views'
  `shown` flipping with the active tab and the hex toggle) and by the real window: `sfoglia.exe three.pdf
  second.pdf` shows exactly one visible `SUMATRA_PDF_FRAME` (the second tab's), the first hidden at the size
  SumatraPDF gave it; a click on the first tab (through the desktop-control tools) shows the first frame placed
  over the panel and hides the second (`runs/C-014-windows-two.png`, `runs/C-014-windows-two-first.png`); the
  window closed through its close message ends both processes. (2) A PDF under another name (`report.txt`
  with a `%PDF-` header, routed here by its signature) was called `TXT`, and pdftoppm said it reads PDF alone:
  the kind now comes from the content (a PDF header is a PDF whatever the name; XPS and OXPS by name for a
  ZIP), pinned with `report.txt` under the pdftoppm stand-ins and with nothing installed. (3) A tab closed
  while drawings were in flight left its folder: the drawings were detached tasks that recreated the folder
  after the pages removed it. Fixed: the pages own their drawing tasks (dropped with them), the folder is made
  once at the start, and a drawing that finishes after the pages are gone removes the folder itself; pinned
  by a zoom change (new drawings in flight) followed by the close. (4) The Windows hint told a Windows user to
  install a Linux package: the source is the platform's now (mupdf.com and a poppler build for Windows on
  Windows, the packages elsewhere), pinned per platform. The `WM_COPYDATA` payload is now built by one function
  the unit test checks (the UTF-16 units and the terminating zero), rather than a helper of the test's own.
