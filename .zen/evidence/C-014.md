## Embedding experiments (2026-10-18, SumatraPDF 3.6 at `C:\Program Files\SumatraPDF`)

Scripts in the session scratchpad (`pdfexp/embed.ps1`, `pdfexp/drive.ps1`), a WinForms panel as the host:

- `SumatraPDF.exe -plugin <hwnd> <pdf>` creates its frame as a child (`SUMATRA_PDF_FRAME`, style
  `WS_CHILD | WS_VISIBLE | WS_CLIPSIBLINGS | WS_CLIPCHILDREN`) of the given window, sized to the parent at that
  moment, with its own toolbar (page field, arrows, view modes, rotation, zoom, find) and the canvas below. The
  document rendered inside the host; `PrintWindow(host, PW_RENDERFULLCONTENT)` captures it with the child.
- The frame does not follow a resize of its parent: `MoveWindow(frame, 0, 0, w, h, TRUE)` resizes it and the
  canvas re-lays out (captured at 600×500 after a 900×700 start).
- `WM_COPYDATA` to the frame with `dwData = 0x44646557` ("DdeW") and the UTF-16 DDE command text drives that
  instance alone, no DDE server involved (several instances register the same `SUMATRA` service, so a real DDE
  conversation could land in the user's own SumatraPDF): `[GotoPage("<path>", 3)]` went to page 3,
  `[SetView("<path>", "continuous", 50)]` set the zoom to 50 % with Sumatra's own notification; both returned 1.
  After a command Sumatra takes the keyboard focus (`GetFocus` and `GetForegroundWindow` were the frame).
- Closing the host window ends the SumatraPDF process on its own (`HasExited` true two seconds later); the
  view still kills it explicitly when the tab closes, so no instance outlives its tab.
- Not tried: `-plugin` with a URL argument (the browser-plugin form), the named-destination command (P-009).

## Design (2026-10-18)

- `src/tools.rs`: `Tool` (SumatraPdf, SevenZip, LibreOffice, Vlc, MuTool, PdfToPpm, PdfInfo), `ToolSet`
  (`from_env`, or `stubbed` for tests: an override per tool, a path or nothing) with `find` (override, else
  `SFOGLIA_<TOOL>` from the environment, else the registered handler and the known install folders, else the
  search path), `refresh` (looks again), `Found { path, version }` (the version resource on Windows read through
  `GetFileVersionInfoW`, `mutool -v` / `pdftoppm -v` otherwise), `status_line` (`SumatraPDF 3.6` /
  `mutool 1.24.9` / `<Tool> at <path>` / the install hint). The hint names the tool, the package or the site, and the
  override variable.
- `src/pdf_host.rs` (Windows only): `SumatraHost::start(exe, pdf, parent_hwnd)` spawns the plugin process;
  `place(bounds)` finds the frame among the parent's children by process id (several PDF tabs share the parent)
  and `MoveWindow`s it when the bounds change; `show(bool)` hides it when the tab is inactive or the hex view is
  on; `command(text)` sends the DDE text by `WM_COPYDATA`; `Drop` kills the process. The parent is the GPUI
  window's HWND from `raw_window_handle::HasWindowHandle` (a headless test window has none: the host is then
  not started and the view says so in its state, not on screen).
- `src/pdf_pages.rs` (both platforms): `Renderer` over `mutool` (`mutool pages` for the count and media boxes,
  `mutool draw -F png -r <dpi> -o <png> <pdf> <n>` per page) or `pdftoppm` with `pdfinfo` from the same package
  (`pdfinfo -f 1 -l N` for the sizes, `pdftoppm -png -r <dpi> -f n -l n -singlefile`), page images decoded by
  the image crate into `RenderImage`s, rendered on demand around the visible range into a temp folder removed
  with the view.
- `src/viewers/pdf_view.rs`: on Windows the Sumatra host when SumatraPDF is found, else the page renderer when
  mutool or pdftoppm is found, else the hint; on Linux the renderer or the hint. The status row names the tool
  and version and, in the page view, the page count, the current page and the zoom; Ctrl+= / Ctrl+- / Ctrl+0
  step the zoom and return to fit-width; `Look again` on the hint re-runs the detection. Without a tool the view
  shows the bytes (the hex view, C-007) under the hint.
- The workspace routes `Family::PdfXps` to the view and carries the `ToolSet` as it carries the rules store;
  `FilePanel::set_active` (the dock's hook) and the hex toggle hide and show the host.
- Fixture: `tests/fixtures/three.pdf`, three pages written by `cargo run -p xtask -- fixtures` (a hand-rolled
  PDF 1.4 with Helvetica text, correct xref offsets), and stub tools under `tests/stubs/` (`mutool.cmd` /
  `mutool.sh`: `-v` prints a version, `pages` prints two pages of different sizes, `draw` copies a fixture PNG;
  a stub that exits 1 for the failure path).

## Implementation notes (2026-10-18)

- Two defects found by the headless tests before any refuter pass. A page whose drawing failed was asked for
  again on every paint (the stand-in renderer run from a copied script could not find its fixture, and the test
  binary spawned a renderer process per frame until killed): a failed `(page, dpi)` is now remembered and not
  asked again until the zoom changes or `Look again` runs; the first complaint stays in the status row. And a
  tab the dock closed stayed in the workspace's list of open files until the next open, so its panel, its view,
  its SumatraPDF process and its folder of drawings lived on: the workspace forgets closed tabs on every render,
  and `the_drawings_folder_goes_with_the_tab` pins the view's drop through a weak handle.
- GPUI's `Window` has a `window_handle` of its own (the `AnyWindowHandle`), which shadows the
  `raw_window_handle` trait method: `raw_window_handle::HasWindowHandle::window_handle(window)` in full.
- The kit's `Root` wraps the window's view: `window.root::<Workspace>()` is `None` in tests, the entity from
  `open_window` is the one to keep.
- A stand-in script copied elsewhere loses its fixtures (`%~dp0` is the copy's folder): the test that makes a
  tool appear later writes a wrapper that calls the stand-in in place.
- The version banner parser takes digits and dots alone (`mutool version 9.9`): a `9.9-stub` would read as none.

## Windows captures (2026-10-18, before the first refuter pass)

- `scripts/windows-capture.ps1` learned two things for this clause: a hosted child window another process owns is
  not part of the GPUI surface `PrintWindow(PW_RENDERFULLCONTENT)` renders, so the script prints each

  and composes it at its place (`hosted=N` in its output); and `FindWindowExW` needs `[NullString]::Value` for
