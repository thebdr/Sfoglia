# C-007 — Hex view for binaries and unknown files — lab notebook

The clause states intent; this file holds the research/spike log, sweeps, and design notes that would otherwise bloat the clause (clause altitude, C-012).

## 2026-10-15: design
- Model (`src/hex.rs`, no GPUI): `HexFile` holds a `memmap2::Mmap` (an empty file cannot be mapped and is held as
  no bytes); rows of 16; `render_row` gives the offset, the hex column split in three at the mark (before, marked,
  after; the separator after the last marked cell goes to "after") and the ASCII column split the same way;
  `line()` joins them into the clause's form, 78 characters wide, the last row padded. Search is
  `memchr::memmem::find` from an offset. Offsets parse as decimal or `0x` hex; byte patterns as hex pairs.
- View (`src/viewers/hex_view.rs`): GPUI's `uniform_list` (only an item count, no per-row sizes; the kit's
  `v_virtual_list` wants a size per row, impossible for 134 million rows) with a `UniformListScrollHandle`.
  Rows are `h_flex` elements with id `("hex-row", index)` and the whole line as aria label; the mark is a
  background on the middle part of each column.
- 32-bit pixels: a list of every row of a 2 GiB file is 2.7e9 px tall; f32 rounds such offsets by hundreds of
  pixels, and the last rows were unreachable (the first headless run showed row 134217728 missing after a go-to
  past the end). Fix: the list holds a window of at most 2^20 rows (2e7 px, exact) around the current position;
  `scroll_to_row` moves the window when the target is outside it or within 4096 rows of an edge, and
  `slide_window_if_near_edge` (called at the start of every render, skipped while a scroll is still pending,
  which would read a stale offset) slides it under the same top row during wheel scrolling.
- The scroll handle's `logical_scroll_top_index` reads child bounds a uniform list never records and always said
  0; `top_row` is computed from the offset and the measured content height instead.
- Chords: the kit's inputs bind ctrl-f (search), ctrl-g, ctrl-h (replace) and ctrl-o themselves, so the hex
  chords are Ctrl+Shift+B (toggle), Ctrl+Shift+G (offset), Ctrl+Shift+F (find), Ctrl+M (mode). In the headless
  test, `dispatch_action(ToggleHexView)` with the hex view focused did not reach the workspace while the chord
  did; the test uses the chord, which is what the clause states.
- The 2 GiB test creates the file with `set_len` (sparse on Linux, allocated on NTFS) under one fixed name, since
  a panicking run leaves it behind; six leftovers once filled the disk and failed the next run at `File::create`.
  Open plus first frame measured 25 to 130 ms; the whole-file search for the end marker runs in the test too.

## 2026-10-15: critic passes
- First pass (commit 4ba4930): refuted, five findings. (1) The forward slide of the row window (`near_end`) was
  exercised by no test; the only wheel scroll went up. Fix: from the start of the 2 GiB file the test scrolls down
  to 4000 rows short of the window's end, asserts the exact top row and the slid window, then scrolls 10 000 rows
  further, past the first window's end. (2) The window was 2^20 rows, more than the "million" the clause states.
  Fix: a million exactly, pinned. (3) The Verification text still named Ctrl+H for the toggle while the
  description and the code say Ctrl+Shift+B. Fix: the text. (4) Nothing checked the mode button's label or its
  click. Fix: the button sits in a wrapper that carries the test id and the label; the test reads "text", then
  "bytes" after Ctrl+M, clicks it back to text and again to bytes. (5) The first-search miss ("not found") was
  never run. Fix: the first search is for text that occurs nowhere; the status and its label read "not found"
  and the mark is unchanged.
- Disk: the record runs failed twice with StorageFull. The first time a critic's scratch target directory (5.8 GB)
  and leftover 2 GiB files had filled the drive; the second time the drive itself was at 2 GB free. The 2 GiB
  test file is now flagged sparse on Windows too (`fsutil sparse setflag`, Linux extends sparsely by itself), so
  the test costs no disk; the build directory's incremental cache and stale test binaries (8 GB) were deleted.
  Searching the end marker across the sparse mapping takes about 8 s (page faults on zero pages) against well
  under a second on a dense file; the test prints both timings and budgets neither.
