# C-004 evidence: open a file and route it to the right viewer

## 2026-10-14: design, from the gpui-kit study
- Dock: `DockSkin::dock_area(id, version, window, cx)` builds the `DockArea`; `add_panel(entity, DockPlacement::Center,
  None, window, cx)` merges a panel into the first centre tab group or starts one; `select_panel(id, ...)` activates a tab.
  A panel implements `gpui_base::dock::Panel` (`panel_name`), `gpui_component::dock::Panel` (`title`),
  `EventEmitter<PanelEvent>`, `Focusable` and `Render`.
- Open dialog: `cx.prompt_for_paths(PathPromptOptions { files, directories, multiple, prompt })` returns a oneshot
  receiver of `Result<Option<Vec<PathBuf>>>`; awaited in `cx.spawn_in(window, ...)`.
- Drop: `on_drop::<ExternalPaths>` on any interactive element, guarded by `can_drop`; the platform delivers file drags
  as an `ExternalPaths` drag value.
- Extension table: generated into `src/generated/families.rs` by the same xtask that writes `FORMATS.md`, from the
  `Family:` slug and `Extensions:` list of each family clause. `txt` moved from the word-processing family to the text
  family (P-002) because P-007 itself says plain txt belongs to P-002.
- Detection rules and their tests live in `src/detect.rs`; signatures: PNG, JPEG, GIF, WebP, TIFF, Photoshop, OpenEXR,
  PDF, 7z, gzip, xz, bzip2, RAR, tar, ZIP (container, not definitive), OLE compound (container), TNEF, MP3, FLAC, Ogg,
  WAV, AVI, MP4 family, Matroska, MPEG program stream.

## 2026-10-14: first refuter pass (refuted) and the fix
- Three real gaps, all bug, in the signature table: (1) ISO media (ftyp), TIFF, Ogg, Matroska and gzip were marked
  definitive although several families share them, so a correctly named heic, avif, m4a, cr3, dng, nef, ogv, mka or
  svgz was routed to the wrong family; (2) the three-letter ASCII prefixes BZh and ID3 fired on plain text, and the
  RIFF forms were matched without the RIFF prefix; (3) only 6 of 27 signatures had a test. Fix: those five are now
  container signatures that never override a known extension; ISO media is told apart by brand (HEIF and AVIF images,
  M4A audio, CR3 raw, movie brands video); bzip2 needs its block magic, ID3 a version byte, RIFF forms the RIFF prefix;
  every signature has a real-header test under a neutral and under its own extension, and the shared-container cases
  the critic listed are asserted (9 detect tests). The clause now states the definitive-versus-container rule explicitly.

## 2026-10-14: second refuter pass (refuted) and the fix
- Gap 1, bug: a tab closed through the dock Close action stayed in the workspace list, so reopening the file called
  select_panel on a panel the dock no longer held and silently did nothing. Fix: the list is pruned against the dock
  (DockArea::panel) before opening and when listing; the UI test now closes a tab with the ClosePanel action, asserts
  the file is gone from open_files, reopens it and asserts a fresh, active tab.
- Gap 2, bug: GIF87a, GIF89a, 8BPS and fLaC are printable ASCII and still fired on prose. Fix: any signature spelled
  entirely in printable text is believed only when the sample does not read as text (PDF excepted, a whole PDF can be
  printable); twelve prose lines starting with signature letters are asserted as text, and the bzip2 real-header case
  carries binary bytes after its block magic as real streams do.
- Clause: a file whose tab was closed is no longer open; opening it again adds a fresh tab.

## 2026-10-14: third refuter pass (refuted) and the fix
- Gap 1, bug: the ISO media check ran before the printable-text rule, so prose with ftyp at offset 4 was a signature.
  Fix: an ISO media header must open with a real box size (three zero bytes); the two prose lines are asserted as text.
- Gap 2, ambiguous_contract: the code exempted PDF from the printable-text rule while the clause stated none. Fix: a PDF
  is recognised only by its full header line (%PDF-d.d plus a line ending), which prose does not have; the clause now
  states this one exception and why (a whole PDF can be printable).

## 2026-10-14: fourth refuter pass (refuted) and the fix
- Gap 1, missing_feature inside the stated rule: the clause names MP3, but only ID3v2-tagged files were recognised; an
  untagged MP3 opens with an MPEG audio frame sync. Fix: frame sync (eleven sync bits plus the Layer III bits) is a
  definitive signature; three sync variants and a JPEG non-match are asserted.
- Gap 2, bug: a UTF-16 byte-order mark alone made a file text. Fix: the units after the mark are decoded and held to the
  same control-character rule as UTF-8 (a cut-off unit or surrogate pair is forgiven); a mark followed by binary is
  binary and routes to hex. The dead text branch for shared extensions was removed; the clause never had it.

## 2026-10-14: fifth refuter pass (refuted) and the fix
- Gap, bug: generic ISO media brands (isom, mp42, dash and the like) were definitive video although audio-only m4a files
  carry them too, so a correctly named m4a with a generic brand was misrouted. Fix: only brands that name a family stay
  definitive (HEIF and AVIF images, M4A and M4B audio, CR3 raw, M4V and QuickTime movies); every other brand is a
  container defaulting to video under an unknown extension. m4a and m4b under isom, mp42 and dash are asserted as audio.
- Sixth pass: holds. Verdict recorded; clause marked verified.

## 2026-10-14: Latin-1 text is text (widened with C-005)
- The C-005 critic found that a Latin-1 source file (bytes that are not UTF-8) was classed binary and never reached the
  text viewer, although the viewer decodes Latin-1. Rule added, as the clause already read it: bytes that are not UTF-8
  are text when none is a control byte beyond whitespace and escape and none is DEL; such a file routes like any text.
  Asserted in src/detect.rs (Latin-1 prose and source are Text(Latin1); Latin-1 bytes mixed with NUL or DEL stay binary).
- Critic pass on the widening (2026-10-15): two wording mismatches, routed as ambiguous_contract. (1) A byte-order
  mark promises its encoding: bytes behind a UTF-8 or UTF-16 mark that do not decode are binary; the clause now says so
  and a UTF-16 case is asserted beside the UTF-8 one. (2) Bytes 0x80 to 0x9F are C1 controls in Latin-1 but punctuation
  in Windows-1252 (smart quotes, dashes, euro), which is what such files are in practice; they count as text, the clause
  says so, and a sample with 0x93, 0x94, 0x96, 0x80 and 0x85 is asserted as text while a backspace byte is not.
