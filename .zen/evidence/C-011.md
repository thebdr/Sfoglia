# C-011 Markdown rendering

## Design (2026-10-17)

- The rendering is the kit's rich text: `gpui_kit::text::TextViewState::markdown` parses on a background task
  (the `markdown` crate 1.0, GFM: tables, task lists, strike-through, footnotes) into a block list rendered by a
  virtualised `gpui::list` when `scrollable`, with code blocks painted by the component's tree-sitter highlighter
  (the same grammars as C-005), images through an `image_source` resolver, links through `on_link_click`, and a
  `reveal_range` / `rendered_text().range_for_source` pair that maps Markdown source offsets to rendered lines.
- `src/markdown.rs` (pure) parses the same source with the same crate into an **outline**: one entry per block
  (kind, depth, text) with the source span, the heading count and a slug per heading. It is what the status row
  summarises, what the toggle uses to carry the place across (block index ↔ source line), what `#fragment` links
  resolve against, and what the tests assert exactly. The kit builds its blocks from the root's children one to
  one, so block indices agree between the two.
- `src/viewers/markdown_view.rs`: `MarkdownView` owns the path, the rich-text state, the raw `TextView` (built at
  open: Markdown files are small, so the text viewer's own disk watch, dirty flag and messages serve from the
  start), `raw_shown`, the outline and the status. Ctrl+Shift+D toggles; going raw puts the cursor on the first line
  of the block at the top of the rendered list (`list_state().logical_scroll_top().item_ix`), going rendered sets
  the state's text from the editor and reveals the block holding the cursor's line. The text viewer's `operations`
  and `reloads` counters are followed as in C-010: messages copied at render time, a reload re-renders. The
  Reload / Keep mine bar is drawn on the rendered side when the text viewer reports a change on disk.
- Links: `http(s)` and `mailto` go to `cx.open_url`; a relative or absolute path is resolved against the file's
  folder and dispatched to the workspace as an `OpenLinkedFile` action; a `#fragment` reveals the heading whose
  slug matches (GitHub's slug rules: lower-case, spaces to hyphens, punctuation dropped).
- Images: a relative or absolute path becomes an `ImageSource::Resource` path, `http(s)` a resource URI, and a
  `data:` URL is decoded from base64 into an `ImageSource::Image`.

## Implementation notes (2026-10-17)

- First build: `src/markdown.rs` (outline, link targets, image sources, slugs, a small base64 decoder, 3 unit
  tests on `tests/fixtures/guide.md`), `src/viewers/markdown_view.rs` (`MarkdownView`), the workspace routing of
  `Family::Markdown` before the text fallback, `PanelView::Markdown` in every match, the `OpenLinkedFile` action
  (a data-carrying action derived with `#[action(namespace = sfoglia, no_json)]`) handled by the workspace, and the
  `ctrl-shift-d` binding in the `MarkdownView` context.
- Kit facts met on the way: the component's `text::TextView` facade has no `image_source`, so the view uses the
  base element `gpui_kit::base::text::TextView` with the state from the component module (one type); image sources
  are `ImageSource::Resource(Resource::Path | Resource::Uri)` in this GPUI; the rich text parses on a background
  task, so headless tests `run_until_parked` after opening and after every toggle; the kit's blocks are the root's
  children one for one, so `ListOffset::item_ix` is an outline index; a `reveal_range` from far below lands the
  block at the bottom edge (block 91 of 120 shows with row 76 at the top in the headless window).
- All five headless tests passed on the first run but one: the grammar lookup takes a file name, not an
  extension (the test, not the code, was wrong). GitHub's slug of "C++ & Rust: 2 things!" has two hyphens, which the
  code produced and the first expectation did not.
