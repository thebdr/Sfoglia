# C-010: Structured data trees

## Design (2026-10-17)

- `src/data.rs` (pure): `Format` from the extension (json, jsonl, xml, yaml/yml, toml, ini); `Tree { format, nodes }` is a
  pre-order arena: each `Node` has `depth`, `end` (one past its subtree, so the children of `i` are `i+1`, then each
  child's `end`, until `end(i)`), `key`, `kind` (`Kind` enum, one label each), `value` (the full text; containers carry
  their entry count), `line` where the parser gives one. Parsers: JSON and JSON Lines through a serde `DeserializeSeed`
  builder over `serde_json::Deserializer` (no intermediate `Value`, so a 50 MB file costs the arena alone); YAML through
  `serde_saphyr::from_str::<serde_json::Value>` (key order kept by `preserve_order`) then a walk; TOML through
  `toml::Table` (`preserve_order`) and its typed `Value` (date-times kept apart); XML through `roxmltree` (elements,
  `@attributes`, text, comments, processing instructions; an element whose only content is text carries it as its
  value); INI by hand (sections, `key = value` or `key: value`, `;`/`#` comments, a line with neither is the error).
  `ParseError { line, column, message }` from each parser's own position (serde_json line/column, saphyr `Location`,
  toml `span()` mapped to a line, roxmltree `TextPos`, the INI line). `path(ix)`: `$`-rooted dotted/bracketed for
  JSON, JSON Lines, YAML and TOML (keys that are not identifiers go in `["..."]`), XPath-style with 1-based sibling
  positions and `@name` / `text()` / `comment()` / `processing-instruction()` for XML, `section.key` for INI.
  `search(text)` lists the nodes whose key or value contains the text case-insensitively. `pretty(format, text)` gives
  the pretty form or the parse error.
- `src/viewers/data_view.rs`: `DataView` owns the tree (or its error), the expanded set, the visible row list (rebuilt
  on every open/close), the selection, the search `InputState` and the match list, the raw `TextView` (built on first
  need: on Ctrl+Shift+D, Ctrl+Shift+P, or at once when the file does not parse), and whether the raw side shows.
  Rows are a `uniform_list` over the visible list, ids `("data-row", row)` with the aria label
  `"{depth}|{key}|{kind}|{value}"`, indented by depth, with an open/close glyph on containers. Actions in the
  `DataView` context: up/down/left/right/enter/space, ctrl-shift-f (focus search), ctrl-shift-c (copy path),
  ctrl-shift-p (pretty-print), ctrl-shift-d (raw text). The status row (`data-status`, `data-path`, `data-matches`)
  names the format, the node count, the selected path and the last outcome.
- `src/workspace.rs`: `PanelView::Data`, routed by `Route::Family(Family::DataTrees)` before the text rule; the panel's
  dirty flag, close guard and Ctrl+S go through the data view's text view; `FilePanel::data_view()` for tests.
- The kit's `TreeState` was ruled out: it clones every visible child `TreeItem` (with its subtree) on each
  expand/collapse, which a million-node tree cannot afford; the hex view's own uniform list pattern fits.
- The kit has no XML or INI grammar: `text::language_for` maps xml to the HTML grammar and jsonl to JSON; INI gets the
  highlighting rules only, and the clause says so.

## Implementation notes (2026-10-17)

- Unit tests in `src/data.rs` (11): the format table, exact arenas for JSON, JSON Lines, XML, YAML, TOML and INI,
  paths for every kind of node, search, pretty-printing of all six formats with the tree unchanged, parse errors
  with line and column for all six, and a generated 50 MB JSON (about 125 000 records, 1.25 M nodes) parsed with the
  exact node count and a deep path. The seed-based JSON builder parses the 50 MB in well under a second even in the
  debug profile.
- Headless tests in `tests/data.rs` (4): the JSON tree's rows, keys, paths, clipboard, search and marks; the raw text
  toggle, pretty-print as an undoable edit, Ctrl+S from both sides, a breaking edit shown as the error; a malformed
  file opening on its text with the cursor on the error line; the root rows of the other five formats.
- Lesson: the kit's `InputEvent::PressEnter` and `Change` events land after the window update ends. The first run of
  the search and dirty assertions failed inside one `update_window` block; the tests now leave the block and
  `run_until_parked()` before asserting, as the C-008 tests already did for typing.
- `replace_all` on the editor emits no `Change`, so the data view calls `TextView::note_edit` after a pretty-print
  to mark the tab modified.
