## C-002: Format support checklist generated from the contract
- **Date:** 2026-10-14
- **Source:** ingest (user-request-2026-10-13#checklist)
- **Description:** `FORMATS.md` is the user-facing checklist of every extension Sfoglia knows: one row per format family listing its extensions, Read status, Write status, the clause that proves it, and who requested it and when. It is generated by one command, `cargo run -p xtask -- formats`, from the clauses of this contract whose description begins with an extension list, so it can never claim more than a verified clause does: a pending clause renders as planned, an unverified clause as in progress, a verified clause as done. The Write flag follows the clause's own write sentence, judged on the part before its first semicolon so that a deferred remainder does not demote a present grant: no sentence (an empty one counts as none), or one opening (in any letter case) with out of scope, no, none, not supported or read-only, renders no; one opening with later or speaking of a later extension renders later; anything else is a present grant and mirrors Read. A clause that merely mentions extensions in prose is not a family; a malformed list entry (a bad token, a missing comma, prose between tokens, more than one parenthesised note) is an error, never a row, and an entry may carry only one parenthesised note after its token. The Requested column names the origin from the clause's provenance (the part before the hash of an ingest tag, or the bare source) and a date: a real calendar date found inside the origin, else the clause's own date; a family with no origin or no real date is an error. New requests, including external ones, enter as a pending clause and appear in the checklist as planned rows. A bare `cargo test` fails while the committed file is stale.
- **Verification:** automated → renders_the_expected_table_for_the_fixture, committed_checklist_matches_the_committed_contract, committed_contract_families_are_exactly_the_clauses_that_start_with_extensions, a_clause_that_mentions_extensions_in_prose_is_not_a_family, a_malformed_extension_token_is_an_error_not_a_row, extension_lists_keep_order_drop_duplicates_and_parentheses, flags_follow_clause_kind_status_and_write_sentence, parses_every_clause_with_its_fields, requested_by_names_the_origin_and_a_real_date | a fixture contract with verified, unverified, pending, prose-mention and non-format clauses renders the exact expected table; the committed `FORMATS.md` must equal the generator's output for the committed contract, and a deliberately stale file was shown to fail a bare `cargo test` (evidence).

## C-004: Open a file and route it to the right viewer
- **Date:** 2026-10-14
- **Source:** ingest (user-request-2026-10-13#core)
- **Description:** A file reaches Sfoglia from the command line (every argument is a path to open), from the Open dialog (Ctrl+O, several files at once), or by dropping it onto the window. Each file is identified first by its extension, looked up in the extension table generated from this contract's family clauses, and then by its content: a definitive signature at the start of the file (PNG, JPEG, GIF, WebP, Photoshop, OpenEXR, PDF, 7z, xz, bzip2, RAR, tar, TNEF, MP3, FLAC, WAV, AVI, MPEG program stream, and an ISO media file whose brand names its family) overrides a misleading extension; a container signature shared by several families (ZIP, OLE compound, TIFF, gzip, Ogg, Matroska, ISO media of unknown brand) never overrides a known extension and only settles an unknown one; an extension listed by several families is settled by a signature naming one of them and otherwise by contract order; a file with no known extension and no signature is text when its bytes decode as text (UTF-8, UTF-16 by its mark, or single-byte text when they carry no byte-order mark, are not UTF-8, and hold no control byte beyond whitespace and escape nor DEL; bytes 0x80 to 0x9F are Windows code-page punctuation and count as text) and binary otherwise; a byte-order mark promises its encoding, so bytes behind one that do not decode are binary; a character, unit or surrogate pair cut off by the end of the sampled bytes is forgiven; and plain text, in any of these encodings, that merely begins with the bytes of a signature is still text; the one signature believed inside text is a PDF's full header line (`%PDF-` with a version and a line ending), because a whole PDF can be printable. The file is then routed to the viewer of its family; text without a family goes to the text viewer, anything binary that no viewer claims goes to the hex viewer, never to an error; an empty file is text. Until a family's viewer exists, its tab shows the file's name, path, size, detected family and the clause that will bring the viewer; a path that cannot be read still opens a tab, which states the error. Each open file is a tab in the centre of a dockable layout, several at once; opening a file that is already open activates its tab instead of adding one, and a file whose tab was closed is no longer open, so opening it again adds a fresh tab. The extension table and the checklist come from the same clauses, so the application and `FORMATS.md` cannot disagree, and a stale table fails `cargo test`.
- **Verification:** automated → every_family_extension_routes_to_its_family, a_definitive_signature_overrides_a_misleading_extension, container_signatures_never_override_a_known_extension, every_signature_is_recognised_with_its_real_header, unknown_extension_is_settled_by_content, shared_extensions_are_settled_by_content_then_contract_order, empty_and_text_files_go_to_text_and_unknown_binary_to_hex, generated_family_table_matches_the_committed_contract, opening_files_adds_tabs_and_reopening_activates_the_existing_tab | exact family and viewer per fixture, exact tab list and active tab in the headless window; manual: the real app launched with two paths on Windows and on Linux shows two tabs, the Open dialog driven on Linux adds a third, and a file dropped on the window by a person opens a tab.

## C-006: Custom highlighting rules with regex and priority
- **Date:** 2026-10-14
- **Source:** ingest (user-request-2026-10-13#core)

When the file does not exist, the panel starts from a commented example, written on the first change.

- **Description:** Any file can be shown as rows of 16 bytes: a hexadecimal offset (eight digits, more when the file needs them), the bytes in two groups of eight, and the bytes as printable ASCII (0x20 to 0x7E, every other byte as `.`), in the form `00000010  48 65 6c 6c 6f 2c 20 77  6f 72 6c 64 0a 00 ff 7f  |Hello, world....|`, the last row padded so the columns stay aligned. The status row names the size in bytes, the row count, the offset of the marked byte and the search outcome. Editing bytes in place (overwrite, not insert) is a later extension of this clause.

## C-008: Edit and save text-based files
- **Date:** 2026-10-14
- **Source:** ingest (user-request-2026-10-13#core)
- **Description:** Every file shown in the text viewer (plain text, source, and the raw form of csv, tsv, json, xml, yaml, toml, markdown, html, dxf and eml until their own viewers arrive) is editable in place: typing, cut, copy, paste, undo and redo, and find and replace through the editor's own panel (Ctrl+F finds, Ctrl+H replaces). A modified tab shows • after its name and "modified" in its status row, and it cannot be closed until it is saved or reverted; Revert in the status row restores the saved text. Ctrl+S writes the file in the encoding, byte-order mark and line endings it was read with; clicking the encoding or the line-endings item in the status row chooses what the next save writes (UTF-8, UTF-8 with BOM, UTF-16 LE, UTF-16 BE, Latin-1, Windows-1252; LF, CRLF, CR), the item says what the file was read with until it is saved, and the choice counts as a modification. A file whose line endings were mixed is written with LF unless another ending is chosen, and its status row says so. A character the chosen encoding cannot hold refuses the save, names the character and its line, and leaves the file untouched. An untouched file is never rewritten, and a file with undecodable units is read-only. The file on disk is compared with what was read every second: when another program changed it, a bar offers Reload (the file is read again and the edits are dropped) or Keep mine (the text on screen stays, counts as modified since it now differs from the file, and the next save overwrites the file). When Reload or Revert cannot read the file (deleted, locked), the text on screen stays, the status row says why, the tab stays modified, and the next save writes the text back, recreating the file. Rendered or binary formats are view-only unless a later clause says otherwise.
- **Verification:** automated → saving_round_trips_every_encoding_and_line_ending, an_edit_is_written_in_the_original_encoding_and_endings, the_status_row_cycles_through_every_encoding_and_ending, typing_marks_the_tab_dirty_and_ctrl_s_writes_the_exact_bytes, undo_redo_cut_paste_and_replace_change_the_buffer_as_stated, a_file_changed_on_disk_is_offered_for_reload, a_modified_tab_cannot_be_closed_until_saved_or_reverted, a_mixed_endings_file_is_written_with_lf_and_says_so, a_file_with_undecodable_units_is_read_only, an_unreadable_file_keeps_the_edits_protected | byte-identical decode-then-encode for every fixture in every encoding and ending, mixed endings written as LF, exact bytes after a known edit in UTF-16, Latin-1, UTF-8 with BOM and CR files, the exact refusal for a character an encoding cannot hold;
