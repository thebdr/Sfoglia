## C-002: Format support checklist generated from the contract
- **Date:** 2026-10-14
- **Source:** ingest (user-request-2026-10-13#checklist)
- **Description:** `FORMATS.md` is the user-facing checklist of every extension Sfoglia knows: one row per format family listing its extensions, Read status, Write status, the clause that proves it, and who requested it and when. It is generated by one command, `cargo run -p xtask -- formats`, from the clauses of this contract whose description begins with an extension list, so it can never claim more than a verified clause does: a pending clause renders as planned, an unverified clause as in progress, a verified clause as done. The Write flag follows the clause's own write sentence, judged on the part before its first semicolon so that a deferred remainder does not demote a present grant: no sentence (an empty one counts as none), or one opening (in any letter case) with out of scope, no, none, not supported or read-only, renders no; one opening with later or speaking of a later extension renders later; anything else is a present grant and mirrors Read. A clause that merely mentions extensions in prose is not a family; a malformed list entry (a bad token, a missing comma, prose between tokens, more than one parenthesised note) is an error, never a row, and an entry may carry only one parenthesised note after its token. The Requested column names the origin from the clause's provenance (the part before the hash of an ingest tag, or the bare source) and a date: a real calendar date found inside the origin, else the clause's own date; a family with no origin or no real date is an error. New requests, including external ones, enter as a pending clause and appear in the checklist as planned rows. A bare `cargo test` fails while the committed file is stale.
- **Verification:** automated → renders_the_expected_table_for_the_fixture, committed_checklist_matches_the_committed_contract, committed_contract_families_are_exactly_the_clauses_that_start_with_extensions, a_clause_that_mentions_extensions_in_prose_is_not_a_family, a_malformed_extension_token_is_an_error_not_a_row, extension_lists_keep_order_drop_duplicates_and_parentheses, flags_follow_clause_kind_status_and_write_sentence, parses_every_clause_with_its_fields, requested_by_names_the_origin_and_a_real_date | a fixture contract with verified, unverified, pending, prose-mention and non-format clauses renders the exact expected table; the committed `FORMATS.md` must equal the generator's output for the committed contract, and a deliberately stale file was shown to fail a bare `cargo test` (evidence).
- **Status:** verified

## C-004: Open a file and route it to the right viewer
- **Date:** 2026-10-14
- **Source:** ingest (user-request-2026-10-13#core)
- **Description:** A file reaches Sfoglia from the command line (every argument is a path to open), from the Open dialog (Ctrl+O, several files at once), or by dropping it onto the window. Each file is identified first by its extension, looked up in the extension table generated from this contract's family clauses, and then by its content: a definitive signature at the start of the file (PNG, JPEG, GIF, WebP, Photoshop, OpenEXR, PDF, 7z, xz, bzip2, RAR, tar, TNEF, MP3, FLAC, WAV, AVI, MPEG program stream, and an ISO media file whose brand names its family) overrides a misleading extension; a container signature shared by several families (ZIP, OLE compound, TIFF, gzip, Ogg, Matroska, ISO media of unknown brand) never overrides a known extension and only settles an unknown one; an extension listed by several families is settled by a signature naming one of them and otherwise by contract order; a file with no known extension and no signature is text when its bytes decode as text and binary otherwise, and plain text that merely begins with the letters of a signature is still text; the one signature believed inside text is a PDF's full header line (`%PDF-` with a version and a line ending), because a whole PDF can be printable. The file is then routed to the viewer of its family; text without a family goes to the text viewer, anything binary that no viewer claims goes to the hex viewer, never to an error; an empty file is text. Until a family's viewer exists, its tab shows the file's name, path, size, detected family and the clause that will bring the viewer; a path that cannot be read still opens a tab, which states the error. Each open file is a tab in the centre of a dockable layout, several at once; opening a file that is already open activates its tab instead of adding one, and a file whose tab was closed is no longer open, so opening it again adds a fresh tab. The extension table and the checklist come from the same clauses, so the application and `FORMATS.md` cannot disagree, and a stale table fails `cargo test`.
- **Verification:** automated → every_family_extension_routes_to_its_family, a_definitive_signature_overrides_a_misleading_extension, container_signatures_never_override_a_known_extension, every_signature_is_recognised_with_its_real_header, unknown_extension_is_settled_by_content, shared_extensions_are_settled_by_content_then_contract_order, empty_and_text_files_go_to_text_and_unknown_binary_to_hex, generated_family_table_matches_the_committed_contract, opening_files_adds_tabs_and_reopening_activates_the_existing_tab | exact family and viewer per fixture, exact tab list and active tab in the headless window; manual: the real app launched with two paths on Windows and on Linux shows two tabs, the Open dialog driven on Linux adds a third, and a file dropped on the window by a person opens a tab.
- **Evidence:** .zen/evidence/C-004.md
- **Status:** pending verification

### P-003: Custom highlighting rules with regex and priority
- **Date:** 2026-10-14
- **Source:** ingest (user-request-2026-10-13#core)
- **Description:** The user defines highlighting rules: a regular expression, a style (foreground, background, bold, italic, underline) and an integer priority. Rules apply on top of syntax highlighting. Where matches overlap, the higher priority wins; equal priority is resolved by earlier start, then by longer match. A rule set is scoped by filename glob (for example `*.log` or `plc_*.txt`) and several sets may apply to one file. Rule sets live in a TOML file in the user's configuration directory, are editable inside the app with immediate re-highlighting, and an invalid regex is reported on the rule, not by failing the file.
- **Proposed verification:** automated: overlap resolution asserts exact winning spans for nested, partially overlapping, adjacent and equal-priority matches; glob scoping asserts which sets apply; a malformed rule file loads the valid rules and reports the bad one by line.
